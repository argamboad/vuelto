## 1. Forced-core-edit log (the headline for Assurance Claim 3)

Building the `Projects` slice **by the intended mechanism** (copying `Notes`) required editing these
**existing platform files** — none of them is "slice code":

| # | File edited | Edit | Avoidable? |
|---|-------------|------|-----------|
| 1 | `src/Infrastructure/Persistence/AppDbContext.cs` | add `public DbSet<Project> Projects` | The exemplar teaches it; strictly, `ApplyConfigurationsFromAssembly` would map the entity from its config alone, but every developer copying `Notes` edits this file, and the harness/tests expect the `DbSet`. |
| 2 | `src/Api/Program.cs` | `AddScoped<ProjectsHandler>()` + `AddScoped<ITenantDataContributor, ProjectsDataContributor>()` + `MapProjects(app)` | **No** — DI + endpoint registration must live here (only `Program.cs` may reference `Features.*`, enforced by `OnlyProgram_ReferencesFeatureNamespaces`). |
| 3 | `src/Infrastructure/Persistence/Migrations/AppDbContextModelSnapshot.cs` | rewritten by `dotnet ef migrations add` | **No** — every schema-bearing slice regenerates the shared snapshot + adds a migration. |

Plus **additive new files in shared projects** (not the `Features/` tree): `src/Core/Entities/Project.cs`
and `src/Infrastructure/Persistence/Configurations/ProjectConfiguration.cs`.

**Verdict:** the ADR-004 "a slice touches only slice code, zero core edits" contract **does not hold for a
slice that introduces its own entity.** It holds only for an endpoint/logic-only slice that reuses existing
entities. This is inherent to the clean-platform layering (entities live in Core, the DbContext + migrations
in Infrastructure), not a bug — but the claim as written is false, and the docs should say "slice code +
its DbSet registration + its migration," matching what the `Notes` exemplar actually does.

## 3. New finding + adversarial confirmations

**ADV-P4-1** · **High (NEW)** · `tests/Api.Tests/ArchitectureTests.cs:267-269` — **the route-uniqueness gate
protects nothing for feature slices.** It collects prefixes with `Regex … MapGroup\("([^"]+)"\)`, but a
slice is *required* by `FeatureFiles_RegisterRoutesViaMapTenantFeatureGroup_NotRawMapGroup` to register via
`MapTenantFeatureGroup("…")` — which does **not** contain the substring `MapGroup(` and never matches.
Confirmed: `grep -oE 'MapGroup\("…"\)' src/Api/Features/` returns **nothing**, so the gate's Features set is
empty; a deliberately-colliding second slice (`/api/projects` twice) **passed** `RouteGroupPrefixes_AreUnique`.
The two arch tests are mutually exclusive — one mandates the helper the other can't see. Compounds Step-0
gap **S0-G1** (the gate also skips `src/Api/Endpoints/`). **Fix:** match `MapTenantFeatureGroup` (and raw
`MapGroup`) and scan `Endpoints/` too — folds into CAND-S0-1 / R-route.

**ADV-P4-2** · **Critical (confirmation of RLS-1)** · demonstrated live — a real `ITenantScoped` slice with a
policy-less migration passes `RlsMigrationGateTests`. The mechanism (Phase 1/2): `IntegrationTestFactory`
runs migrations *then* `RlsTestSetup.ProvisionAsync` applies `RlsDdl.StatementsFor(model)`, back-filling the
`Projects` policy before the gate inspects `pg_policies`. **This is the single most important must-fix** —
Phase 4 elevates RLS-1 from "traced" to "reproduced end-to-end on a slice the way a downstream app would
write it."

**ADV-P4-3** · **confirmation of TR-4** · `dotnet ef migrations add AddProjectsThrowaway` produced a
migration that creates the `Projects` table + index with **no RLS DDL** — EF does not scaffold it and
nothing in the workflow prompts for it. The `RlsDdl.StatementsFor` step is purely manual and undocumented in
the add-a-slice checklist. A slice author following the intended mechanism silently ships an unprotected
tenant table.

**ADV-P4-4** · **confirmation of LB-TEN-1 / R82** · nothing forces the slice's `ITenantDataContributor` to be
registered. The user-axis has `EveryUserKeyedEntity_IsWiredIntoAccountErasure`; there is no tenant-axis
equivalent. A slice that adds `Project` but omits `ProjectsDataContributor` would orphan its rows on
dissolve and omit them from export **with a fully green suite** (the dissolution tests seed only
widget/audit/subscription, never a new slice's table). Demonstrated by absence.

**ADV-P4-5** · **confirmation of TR-5** · copying the `Notes` exemplar reproduced the anonymous-error-object
smell verbatim — `ProjectsEndpoints.cs` returns `Results.BadRequest(new { error = "invalid_request", … })`
instead of the R18-blessed shared `ErrorResponse`. The exemplar actively teaches the banned shape to every
slice that clones it.

## 4. Composability findings (second-slice + migration/config/i18n/DI)

- **Migrations compose.** The generated migration got a distinct `20260715010744` timestamp and sorts after
  the existing set — two slices get distinct timestamps and apply in filename order; no misorder. Table
  collisions are separately gated by `TenantScopedEntities_MapToDistinctTables` (green).
- **Routes: distinct prefixes coexist, collisions are undetected.** `/api/notes` + `/api/projects` register
  and serve independently; but collision *detection* is broken (ADV-P4-1).
- **i18n is NOT slice-scoped.** There is one shared client bundle (`src/Shared.Ui/Resources/AppStrings.resx`
  + `.es.resx`) and **zero** per-feature resx (Phase-4 grep: `Features/` resx count = 0). A client-facing
  slice must add its keys to the shared bundle; there is no key-namespacing convention and no collision gate
  (R72 covers EN↔ES *parity*, not per-slice key collisions). Not a live break — server slices don't
  localize — but a real composability limitation the first client-bearing downstream slice will hit.
- **DI composes.** `AddScoped` handler + a second `ITenantDataContributor` registration resolved with no
  ordering issue; contributors are collected as a set, so registration order doesn't bite.

## 6. Generation-scenario notes

- **Slice code is cleanly separable** from core (own folder, own DTOs, own contributor) and the `Notes`
  exemplar is present and exemplary in shape — but it teaches two anti-patterns a generated app inherits:
  the anonymous error object (TR-5/ADV-P4-5) and the *absence* of an RLS-policy migration step (TR-4/
  ADV-P4-3), because `Notes`'s own policy lives in the frozen platform RLS migration rather than in the
  slice, so the exemplar never demonstrates the step a real slice must perform.
- A generated app inherits the throwaway-masking behavior of the RLS test harness (RLS-1): its own new
  slices will look protected in tests and be unprotected in production until RLS-1 is fixed.

## 8. Foundation-readiness verdict

**Ready with fixes — not ready to generate the first real app as-is.** The core-provided isolation
(EF filter, write stamping, RLS-when-provisioned, auth policy) is genuinely inherited by a new slice with no
re-implementation — the foundation's *mechanisms* are sound. What is **not** sound is the ring of
*enforcement gates* meant to make those guarantees un-forgettable for a downstream author: the RLS gate
can't fail, the route-collision gate can't match the mandated helper, the tenant-axis dissolution/export
canary doesn't exist, and the exemplar teaches a banned error shape and omits the RLS-migration step. Each is
a small, well-scoped fix.

**Must-fix before generating the first real app** (all already have candidate rules — Phase 4 sets their
order):
1. **RLS-1 / R36** — split `RlsTestSetup` so the migration-gated DB gets policies from migrations only; the
   gate must fail for a policy-less tenant table. *(ADV-P4-2 — the keystone.)*
2. **ADV-P4-1** — fix `RouteGroupPrefixes_AreUnique` to match `MapTenantFeatureGroup` and scan
   `src/Api/Endpoints/` (folds into CAND-S0-1). One-line regex + directory fix; currently protects nothing.
3. **LB-TEN-1 / R82** — add the tenant-axis dissolution+export canary so a slice can't orphan/omit its data.
4. **TR-4 / R70** — document the `RlsDdl.StatementsFor` migration step in the add-a-slice checklist + PR
   template (ideally scaffold it), so a slice author doesn't ship a policy-less table.
5. **TR-5 / R71** — fix the `Notes` exemplar to use `ErrorResponse`, and ban `new { error` in `Features/**`,
   so slices stop cloning the banned shape.

Non-blocking but recommended: correct the ADR-004 "zero core edits" wording to match reality (§1);
introduce per-slice i18n key-namespacing guidance (§4).
